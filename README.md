# SS14 Social Rating Bot 1.0

Асинхронный Discord-бот социального рейтинга для **нескольких Discord-серверов с изолированными данными**. Каждый сервер включается собственной командой `/rating setup`. Python 3.12+, discord.py, SQLAlchemy 2, SQLite, Alembic. Содержимое сообщений не сохраняется и не анализируется.

## Правила

- Новый участник начинает с **800** (класс «Обычный гражданин»). Начальная сумма записывается отдельной операцией `opening` один раз при создании профиля. **Уже существующие балансы не меняются** при обновлении.
- Не менее **5** обычных сообщений за расчётный период дают **+25**, один раз за период.
- Взыскание уполномоченного модератора: **−50**, обязательна причина. Нижнего предела и дневного лимита взысканий нет.
- Администратор может один раз отменить взыскание: новая компенсирующая операция на сумму исходного взыскания: **+50** для новых взысканий или **+100** для старых взысканий на 100. Исходная запись остаётся в журнале.
- Администратор может вручную выдать **от 1 до 1 000 000** баллов за одну команду `/rating give`, указав причину. Выдача хранится в журнале отдельной операцией и не отменяется командой отмены взыскания.
- Период: **18:00 предыдущего дня включительно → 18:00 текущего дня исключительно, Europe/Kyiv**. Летнее/зимнее время учитывается через IANA, поэтому период может длиться 23 или 25 часов.
- Учитываются только обычные текстовые каналы каждого настроенного сервера, отдельно для него. Личные сообщения, ненастроенные серверы, боты, webhook, системные сообщения, threads, форумы и голосовые каналы не учитываются. Удаление уже учтённого сообщения не отменяет активность.

Текущий рейтинг равен сумме операций журнала: **стартовые начисления + ежедневные начисления − взыскания + возвраты при отменах + ручные выдачи**. Новые ежедневные начисления равны 25, новые взыскания равны 50. Старые операции на 50/100 сохраняют исходные суммы и не пересчитываются. У новых профилей стартовая операция равна 800; прежним профилям она задним числом не добавляется.

### Социальные классы

Класс автоматически определяется балансом и служит отображаемой характеристикой, без автоматических наказаний или новых полномочий:

| Рейтинг | Класс | Цвет |
|---|---|---|
| 499 и ниже, включая отрицательный | Неблагонадёжный | Красный |
| 500–799 | Под наблюдением | Оранжевый |
| 800–1099 | Обычный гражданин | Синий |
| 1100–1499 | Благонадёжный | Зелёный |
| 1500 и выше | Образцовый гражданин | Золотой |

`/rating profile` и `/rating user` публикуют карточку **для всех в канале вызова**. Профиль показывает упоминание участника, **социальный рейтинг**, **социальный класс** и отдельный баланс **кредитов**. Счётчики сообщений, дней и взысканий из карточки скрыты; учёт и история сохраняются.

Нет магазинов, уровней, автоматических наказаний, анализа текста, веб-панели или интеграции с игровым сервером. Классы и ручная выдача добавлены по уточнённому запросу и заменяют соответствующие ограничения первоначального ТЗ.

## Кредиты: отдельная валюта

Рейтинг и кредиты — разные балансы. Начальный рейтинг нового профиля — 800, начальные кредиты — **0**. Старым профилям при обновлении также создаётся нулевой кредитный баланс; уже завершённые периоды не получают кредиты задним числом.

В 18:00 Europe/Kyiv участник с не менее чем пятью засчитанными сообщениями за завершённый период получает **+25 рейтинга** и кредиты по классу:

| Класс | Кредиты за активный период |
|---|---:|
| Неблагонадёжный | 0 |
| Под наблюдением | 10 |
| Обычный гражданин | 20 |
| Благонадёжный | 30 |
| Образцовый гражданин | 50 |

Класс для кредитов фиксируется **до +25 рейтинга этого периода**. Например, при рейтинге 799 начислят 10 кредитов и +25 рейтинга; для следующего активного периода класс уже будет «Обычный гражданин» и начисление составит 20 кредитов. В журнале кредитов сохраняются фактический исходный рейтинг и класс; даже начисление 0 кредитов имеет запись аудита. Менее пяти сообщений не даёт ни ежедневного рейтинга, ни кредитов.

При восстановлении нескольких незавершённых периодов они обрабатываются последовательно по времени. Основа каждого начисления — фактический рейтинг на момент обработки данного периода, до его +25; исторический класс на дату простоя не реконструируется. Выдача `/rating give`, взыскания и отмены меняют только рейтинг и не списывают/возвращают кредиты. Топ также строится по рейтингу.

Рейтинг, кредиты и сводка периода фиксируются одной транзакцией. Повторная обработка не начисляет валюту повторно. Сводка разделяет суммы рейтинга и кредитов, а история показывает единицы каждой операции. Магазинов, переводов валюты и ручной выдачи кредитов пока нет.

## Команды

| Команда | Доступ | Действие |
|---|---|---|
| `/rating setup` | Discord Administrator | Подключить сервер и выбрать канал ежедневной сводки, роли и канал логов |
| `/rating profile` | Все | Собственный социальный рейтинг, класс и кредиты |
| `/rating user user` | Все | Социальный рейтинг, класс и кредиты выбранного участника |
| `/rating top [social_class]` | Все | Публичный рейтинг, необязательный фильтр по одному из пяти классов, 10 участников на странице |
| `/rating history` | Все | Собственная история рейтинга и кредитов с пагинацией |
| `/rating punish user reason` | Модераторы, администраторы | Взыскание −50 |
| `/rating give user amount reason` | Администраторы | Выдать 1–1 000 000 баллов с причиной |
| `/rating undo punishment_id reason` | Администраторы | Отмена конкретного взыскания |
| `/rating log user` | Модераторы, администраторы | Полная история выбранного участника |
| `/rating status` | Администраторы | Состояние периодов, начислений и восстановления |

В топе одинаковый баланс даёт одинаковое место (например, **1, 1, 3**). Внутри равного баланса порядок стабилен по Discord ID. Место при выборе класса рассчитывается среди участников этого класса. Просмотр собственного места не создаёт новый профиль. Профили и топ публичны. Успешные выдачи, взыскания и отмены также публикуются в канале вызова: подтверждение содержит участника, сотрудника, изменение и итог рейтинга, причину, дату и ID операции (для отмены — исходное взыскание). Личная история, журнал, статус и настройка остаются приватными.

**Почему `/rating profile`, а не голая `/rating`:** Discord Application Commands не позволяют одной команде одновременно быть исполняемой корневой командой и группой с подкомандами. Поэтому собственный профиль доступен через `/rating profile`, а остальные команды остаются в группе `/rating`.

Все пользовательские и административные команды работают в пределах текущего сервера. До `/rating setup` рейтинг и активность на нём не учитываются. Настройку может выполнять только участник с Discord-разрешением Administrator.

Полномочия проверяются серверной частью бота. Если список административных ролей сервера пустой, административные команды доступны только пользователям с Discord-разрешением **Administrator**. Обычным участникам доступ не открывается. Если ID административных ролей сервера заданы, доступ определяется **только ими**, без автоматического обхода через Administrator. Список модераторских ролей добавляет модераторов по ID; пустой список не даёт модераторских прав никому дополнительно. Названия ролей не используются. Причина взыскания, отмены и ручной выдачи должна содержать от 1 до 500 символов после удаления пробелов по краям. Подробные истории, ошибки авторизации и проверки ввода приватны. Причины успешных выдач, взысканий и отмен **публичны**, даже если отдельный канал модерации отключён. Не передавайте в причинах пароли, персональные документы и другие секреты. При ошибке после публичного подтверждения обработки бот показывает только общее уведомление в канале; подробности доступны автору приватно.

## 1. Создать Discord Application и бота

1. Откройте [Discord Developer Portal](https://discord.com/developers/applications), создайте приложение.
2. В разделе **Bot** создайте/настройте бота. Сохраните токен в локальном `.env`, не в коде и не в Git. Если токен раскрыт, немедленно перевыпустите его.
3. Боту нужны обычные Gateway Intents **Guilds** и **Guild Messages**. Привилегированный **Message Content Intent** для подсчёта не нужен: бот не читает текст сообщений. Полный список участников также не загружается.
4. В **OAuth2 → URL Generator** выберите scopes `bot` и `applications.commands`.
5. Выберите необходимые разрешения и пригласите бота на нужные серверы. На каждом сервере его администратор отдельно выполняет `/rating setup`. Не выдавайте ему `Administrator`.

Минимальные разрешения:

- **View Channels** и **Read Message History** в текстовых каналах, активность которых нужно учитывать и восстанавливать;
- **Send Messages**, **Embed Links**, **View Channels**, **Read Message History** в канале ежедневных сводок и закрытом канале модерации;
- участникам нужны разрешения **Use Application Commands** в каналах, где доступны команды.

Без доступа к истории точность восстановления после простоя не гарантируется. Ошибки прав и неполнота отражаются в статусе и служебном журнале; бот не придумывает пропущенные сообщения.

## 2. Подготовить роли и каналы

Включите режим разработчика в Discord: **Настройки пользователя → Расширенные → Режим разработчика**. Используйте «Копировать ID» для сервера, ролей и каналов.

Создайте:

- канал ежедневной сводки, например `#соц-рейтинг`;
- при необходимости **закрытый** канал взысканий, например `#логи-рейтинга`.

Выполните `/rating setup` от учётной записи с Discord-разрешением Administrator и выберите канал ежедневной сводки. Это явное подключение **только текущего сервера**. Канал сводки обязателен при настройке. Роли модераторов/администраторов и закрытый канал логов необязательны; без административных ролей используются права Administrator текущего сервера. Без канала модерации операции сохраняются в базе и доступны через `/rating log`, но отдельные сообщения в канал не отправляются.

Бот проверяет принадлежность выбранных каналов/ролей этому серверу и свои права. Настройка другого сервера не копирует пользователей, балансы, историю или очередь уведомлений. Повторная настройка текущего сервера меняет его параметры, сохраняя данные и первоначальный момент подключения. Сообщения до этого момента не засчитываются и не восстанавливаются из истории.

Если отключить ранее настроенный канал модерации, уже созданные уведомления сохранятся в очереди и смогут отправиться после повторного включения; новые взыскания, отмены и ручные выдачи без канала записываются только в журнал базы. Старый модераторский backlog не блокирует ежедневные сводки.

Если канал модерации настроен, у него запретите **View Channel** для `@everyone` и посторонних ролей. Разрешите просмотр только настроенным модераторам/администраторам и боту. Не добавляйте посторонних пользователей через индивидуальные разрешения. Бот проверяет приватность перед публикацией; при неподходящих правах уведомление остаётся в очереди. Владелец сервера и роли с Discord-разрешением Administrator технически обходят канальные запреты; это ограничение Discord, а не обещание бота скрыть записи от владельца.

## 4. Настроить `.env`

Для нового развёртывания обязательно задайте только `DISCORD_TOKEN`. Серверы, каналы и роли выбираются через `/rating setup` в Discord. Пример:

```dotenv
DISCORD_TOKEN=ваш_секретный_токен
DATABASE_URL=sqlite+aiosqlite:///./data/rating.db
START_RATING=800
DAILY_REWARD=25
PUNISHMENT_AMOUNT=50
MIN_MESSAGES=5
PAYOUT_TIME=18:00
TIMEZONE=Europe/Kyiv
LOG_LEVEL=INFO
```

`GUILD_ID`, `LEGACY_GUILD_ID`, `DAILY_REPORT_CHANNEL_ID`, `ADMIN_ROLE_IDS`, `MODERATOR_ROLE_IDS` и `MODERATION_LOG_CHANNEL_ID` в `.env` оставлены для переноса прежней односерверной установки. Для нового развёртывания оставьте их пустыми. Импорт старой базы по умолчанию выключен. Только для её переноса оператор явно задаёт `LEGACY_GUILD_ID` — ID исходного сервера, подтверждённый по старой конфигурации. Он должен совпадать с `GUILD_ID`; также требуется старый канал сводок. Бот не угадывает принадлежность базы по новому приглашению или настройке. Не указывайте новый сервер вместо исходного: это явно привязывает прежние данные к указанному владельцу.

`DATABASE_URL` задаёт базовый путь. Для `sqlite+aiosqlite:///./data/rating.db` реестр настроек располагается в `data/rating.guilds/registry.db`, а новые серверы получают `data/rating.guilds/<guild_id>.db`. Импортированная старая база сохраняет исходный путь `data/rating.db`. Реестр хранит связь ID сервера с его базой; не копируйте базу одного сервера поверх другого.

Пути разрешаются относительно рабочей директории процесса. Для systemd рекомендуется абсолютный базовый URL `sqlite+aiosqlite:////opt/ss14-social-rating/data/rating.db`.

Утверждённые правила v1.0 заданы явно в конфигурации и проверяются при запуске: значения, отличные от 800/25/50/5 и 18:00 Europe/Kyiv, отклоняются. Изменение правил требует новой согласованной версии, а не скрытой правки рабочего `.env`.

Файл `.env`, база, резервные копии и логи исключены из Git. Не публикуйте их в issues и не отправляйте токен вместе с диагностикой. При неверных обязательных настройках запуск завершается с ошибкой.

## 5. Создать базу, применить миграции и запустить

```bash
mkdir -p data
. .venv/bin/activate
python -m bot.main
```

Реестр создаётся при запуске. При первом `/rating setup` бот создаёт отдельную базу сервера и применяет к ней Alembic-миграции. Не создавайте таблицы вручную. Alembic — источник схемы и истории изменений каждой базы сервера. SQLite использует WAL, внешние ключи и ожидание занятых блокировок. Операции баланса, журнал и исходящие уведомления фиксируются транзакционно. Уникальные ограничения защищают ежедневные начисления, события сообщений и Discord interactions от повторов.

Запускайте **один процесс бота на один реестр и Discord-токен**. Поддержка конкурентных транзакций не означает поддержку двух независимых Gateway-потребителей/планировщиков как режима развёртывания. Не размещайте активную SQLite-базу на сетевой файловой системе. Ограничьте доступ к каталогу данных учётной записью службы.

## 6. Проверить работу

1. Выполните `/rating setup` на тестовом сервере и проверьте выбранный канал сводки. Для административных проверок используйте учётную запись с настроенной административной ролью или с Discord-разрешением Administrator, если список административных ролей пуст.
2. Выполните `/rating profile`: новый профиль имеет 800 рейтинга, класс «Обычный гражданин» и 0 кредитов.
3. Напишите пять сообщений в обычном доступном текстовом канале. Прогресс сообщений намеренно не показывается в упрощённом профиле; результаты учёта проверяются по ежедневному начислению и административному статусу.
4. Проверьте `/rating status`: ближайшее начисление в 18:00 по Киеву.
5. После завершения периода проверьте +25 рейтинга, кредиты по классу до начисления и одну сводку. Дополнительные сообщения в том же периоде не дают дополнительного начисления.
6. Выполните взыскание с причиной, затем отмену по возвращённому ID. Убедитесь, что обе записи есть в `/rating log`; если канал модерации настроен, проверьте также сообщения в нём.
7. Проверьте `/rating give user amount reason` с небольшой суммой и убедитесь, что баланс и класс пересчитались, а выдача видна в истории.
8. Для проверки без ожидания реального времени используйте автоматические тесты, подставляющие время. Не меняйте часы production-сервера и не редактируйте баланс SQL-запросами.

## Надёжность, отключения и неполные данные

Текущие балансы рейтинга и кредитов хранятся отдельно для быстрого чтения, но каждое изменение сопровождается неизменяемой записью операции. Отмена создаёт компенсирующую запись на фактическую сумму исходного взыскания, включая старые взыскания на 100. Новые события и восстановленные сообщения дедуплицируются по ID.

При перезапуске/переподключении бот восстанавливает доступную историю через Discord API и проверяет незавершённые периоды. Ограничения Discord, удалённые до восстановления сообщения, недоступные/удалённые каналы и глубина хранения могут сделать историю неполной. Такие ограничения не скрываются: проверьте `/rating status` и журнал службы. Удалённое во время простоя сообщение восстановить через Discord невозможно.

Временные ошибки получения истории откладывают начисление до повторной попытки. При известной недоступности истории из-за прав или удалённых каналов бот начисляет по подтверждённым сообщениям и помечает период и сводку как неполные.

Начисление и доставка уведомления разделены. Если Discord недоступен, зафиксированный баланс не откатывается: очередь повторяет только отправку. Возможен дубликат уведомления при сбое после успешной отправки, но до сохранения её подтверждения. **Exactly-once для Discord-сообщений не обещается.** Балансовая операция при этом не повторяется.

## Резервное копирование и восстановление

Сохраняйте **реестр и все базы серверов**, включая исходный `rating.db`, если он был импортирован. Одна копия `rating.db` не сохраняет многосерверную установку. Реестр содержит настройки ролей/каналов и абсолютные пути к базам.

Встроенная команда использует SQLite Backup API и безопасна при WAL. Не копируйте активный `.db` обычной файловой командой: часть данных может находиться в WAL.

```bash
python -m bot.backup data/rating.guilds/registry.db /path/to/backups/registry-2026-10-30.db
python -m bot.backup data/rating.guilds/123456789012345678.db /path/to/backups/guild-123456789012345678-2026-10-30.db
# Повторите для каждой зарегистрированной базы и, при наличии, исходной импортированной базы.
```

Команда проверяет целостность и внешние ключи, выставляет права 0600 и не перезаписывает существующий файл. Для согласованного полного комплекта остановите службу перед копированием всех баз и реестра: это исключит изменение настроек между отдельными снимками. Храните несколько поколений в закрытом месте; копии содержат причины взысканий и ID участников.

Восстановление:

1. Остановите службу `sudo systemctl stop ss14-rating`.
2. Сохраните существующий каталог данных отдельно, включая WAL/SHM, для отката.
3. Восстановите проверенные копии реестра и всех баз **по тем же абсолютным путям**, которые записаны в реестре. Не подменяйте базу одного сервера базой другого.
4. Переместите старые `.db-wal` и `.db-shm` вместе со старыми файлами: они не должны оставаться рядом с восстановленными базами.
5. Верните владельца и права служебной учётной записи. При необходимости примените миграции к каждой базе сервера командой `DATABASE_URL=sqlite+aiosqlite:////полный/путь/сервер.db python -m alembic upgrade head`. К `registry.db` эти миграции не применяются.
6. Запустите службу и проверьте `/rating status`, профиль и историю **на каждом сервере**.

Копия возвращает состояние на момент её создания. Модераторские действия и ручные выдачи после этой точки не восстанавливаются из Discord автоматически. Для переноса на другие абсолютные пути требуется отдельная аккуратная миграция реестра; не редактируйте связи наугад.

## Постоянная работа через systemd

Пример рассчитан на `/opt/ss14-social-rating` и отдельного пользователя `ss14-rating`. Создание пользователя/службы требует прав администратора VPS.

```bash
sudo useradd --system --home /opt/ss14-social-rating --shell /usr/sbin/nologin ss14-rating
sudo chown -R ss14-rating:ss14-rating /opt/ss14-social-rating
sudo cp deploy/ss14-rating.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now ss14-rating
sudo systemctl status ss14-rating
sudo journalctl -u ss14-rating -f
```

До запуска проверьте пути в unit-файле, создайте venv и настройте `.env`. Новые базы будут созданы при `/rating setup`. Служба перезапускается после ошибки. Следите за свободным диском: WAL, база и служебный журнал требуют места. Резервные копии храните вне каталога активной базы; обеспечьте ротацию journal и копий.

## Обновление

1. Ознакомьтесь с изменениями и сделайте проверенную резервную копию.
2. Остановите службу.
3. Обновите код до нужной версии (`git pull --ff-only` только при чистой рабочей копии).
4. В venv выполните `python -m pip install -r requirements.txt`.
5. Примените `alembic upgrade head` к каждой зарегистрированной базе сервера, указывая её `DATABASE_URL`, и запустите тесты. Реестр `registry.db` не является базой рейтинга и не требует этой команды.
6. Запустите службу и проверьте логи и `/rating status` на каждом сервере.

Не откатывайте код поверх несовместимой новой схемы. Для отката используйте согласованную версию кода и копию базы.

## Тестирование

```bash
. .venv/bin/activate
python -m pip install -r requirements-dev.txt
python -m pytest -q
```

Для воспроизводимого окружения есть `requirements.lock` с версиями всех зависимостей проверенного окружения (включая инструменты тестов): `python -m pip install -r requirements.lock`. Основной `requirements.txt` задаёт допустимые диапазоны версий.

Тесты создают временные SQLite-базы и не требуют токена/реального подключения Discord. Они проверяют порог, дедупликацию, повторные начисления, сохранность после перезапуска, отрицательный рейтинг, отмены, роли, конкурентные транзакции, границы времени/DST, уведомления и резервную копию. При обновлении миграция сохраняет старые балансы, журнал и ссылки на отменённые взыскания. Стартовые 800 не выдаются повторно старым участникам.

Успешные unit/integration-тесты не заменяют проверку фактических прав и Gateway на вашем Discord-сервере.

## Какие данные хранятся

- Discord ID участников, модераторов, сообщений и interactions;
- балансы рейтинга и кредитов, число сообщений за период, даты начислений;
- отдельный журнал кредитов с рейтингом и классом, использованными при начислении;
- операции, причины взысканий/отмен/ручных выдач и ссылки между ними;
- состояние восстановления, периоды с неполнотой, техническая очередь уведомлений.

**Текст сообщений не хранится.** Технические ID сообщений завершённых периодов удаляются по сроку `MESSAGE_RETENTION_DAYS` (по умолчанию 35 дней); глубина восстановления задаётся `RECOVERY_LOOKBACK_DAYS` (по умолчанию 35 дней). Для незавершённых периодов дедупликация сохраняется до завершения. Агрегаты активности, балансовый журнал и причины взысканий сохраняются для аудита, пока оператор сохраняет базу. Не обещайте участникам удаления этих данных, если не организовали отдельную согласованную процедуру. Резервные копии имеют отдельную политику хранения, которую задаёт оператор.

## Диагностика

- Нет slash-команд: проверьте scopes приглашения и права Use Application Commands; бот синхронизирует команды отдельно при подключении к каждому серверу. Если сервер не настроен, сначала выполните `/rating setup`.
- Активность не растёт: обычный ли это текстовый канал, доступен ли он боту, не бот/webhook/thread ли отправитель/источник.
- Нет сводки: проверьте очередь/статус, ID канала, Send Messages и Embed Links. Не запускайте начисление вручную повторно через SQL.
- Нет модераторских логов: при пустом `MODERATION_LOG_CHANNEL_ID` это штатно, история остаётся в SQLite и `/rating log`. Если канал задан, проверьте его закрытость и все разрешения.
- SQLite locked: убедитесь, что не запущен второй бот и нет стороннего процесса с долгой write-транзакцией; база должна находиться на локальном диске.
- Неполный период: проверьте доступ к истории, длительность простоя, удалённые каналы и глубину восстановления. Не считайте неполные данные точными.

### Сеть через прокси

Если среда требует HTTP(S)-прокси, задайте `DISCORD_PROXY` в локальной конфигурации. Он передаётся Discord-клиенту для REST и Gateway; по умолчанию прокси не используется. Значение с учётными данными не публикуйте.

### Прокси и задержка ответа Discord

`DISCORD_PROXY` необязателен. На обычном VPS с прямым доступом к Discord оставьте его пустым. Если окружение требует HTTP(S)-прокси, задайте разрешённый оператором адрес. URL с паролем относится к секретам: не публикуйте `.env` и не включайте его в диагностические сообщения.

При настроенном прокси бот сохраняет HTTP-соединения до 75 секунд и раз в 20 секунд выполняет служебный запрос к Discord для поддержания соединения. Это снижает риск задержки при открытии нового прокси-туннеля, но не гарантирует укладывание в лимит первоначального ответа Discord на ограниченном хосте. В журнале записываются возраст interaction при начале ответа и длительность HTTP-запроса, без токена interaction. Если первоначальный ответ уже просрочен (`Unknown interaction`, код 10062), команда не доходит до работы с базой; повторная попытка отправить ошибку по тому же просроченному interaction не выполняется. При повторяющихся задержках используйте хост с устойчивым доступом к Discord.
